content_data Schema Reference
content_data — Dynamic Schema Resolution
The Model
# /compose receives a flat content_data dict.
# DD looks up the mandated Forma for doc_type.
# Each PERMISSIVE field in the Forma maps to a key in content_data.
# FIXED fields are populated by DD from the Forma definition — not by the caller.
# Unknown keys in content_data → ORPHANED block at foot of document.
# Missing REQUIRED PERMISSIVE keys → compose fails with SCHEMA_MISMATCH.

POST /compose
{
  "doc_type": str,                     # registered doc type name
  "content_data": dict[str, Any],    # keyed by PERMISSIVE field name
  "output_targets": list[str]        # ["wiz","md","pdf"] — subset allowed
}
Example A — Expositio
Caller sends
{
  "doc_type": "Expositio",
  "content_data": {
    "CORPUS": "App overview text…",
    "TABULA": {
      "headers": ["Key","Value"],
      "rows": [["Stack","PyQt6"]]
    },
    "ZONA": [...]
  },
  "output_targets": ["wiz","md"]
}
DD resolves
Forma: Expositio Arcana v3
TITULUM ← from Forma + caller meta
CAPUT I ← from Forma (FIXED)
CORPUS ← content_data["CORPUS"] ✓
TABULA ← content_data["TABULA"] ✓
DIVISOR ← from Forma (FIXED)
ZONA ← content_data["ZONA"] ✓
SIGILLUM ← from DD at emit time
→ EMIT SUCCESS
Example B — Lore Card (with failures)
Caller sends
{
  "doc_type": "Lore Card",
  "content_data": {
    "LORE_BODY": "Entity background…",
    "UNKNOWN_KEY": "Orphan data"
    # missing REQUIRED: ENTITY_NAME
  },
  "output_targets": ["wiz","md","pdf"]
}
DD resolves — failure path
Forma: Loridex Forma v4
ENTITY_NAME ← MISSING — REQUIRED
LORE_BODY ← content_data["LORE_BODY"] ✓
UNKNOWN_KEY ← ORPHANED → foot block

→ SCHEMA_MISMATCH
{
  "error": "SCHEMA_MISMATCH",
  "missing_required": ["ENTITY_NAME"],
  "orphaned_keys": ["UNKNOWN_KEY"]
}
No files emitted. Caller receives error.
