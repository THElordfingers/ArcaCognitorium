Let me take stock of what's actually in the spec versus what's missing.

What's already in the design:

The distillation system (Phase 5) is the primary efficiency mechanism — fat/muscle classification compresses long threads before they overflow the context budget. The context bar in the status layer gives the Wizard real-time visibility into fill percentage. The routing system (Phase 7) directs simple messages to gpt-4o-mini instead of gpt-4o, which is the single biggest cost lever. The Tome and Grimoire have explicit token budgets (600 and 800 respectively) with enforcement logic. The Assessor uses the precise sampling profile which caps max_output_tokens at 1500.

What's underspecified or missing entirely:

Several gaps that could quietly drain tokens:

Chronicle retrieval is unbounded — the spec says "top-k retrieval" but never defines k, never sets a token budget for injected Chronicle entries, and never specifies what happens when multiple Chronicle hits are all injected. A busy Chronicle could inject thousands of tokens silently.
Interruption responses have no hard token cap — the interruption context (primary message + full response + Entity instruction + task prompt) could be enormous. The task prompt says "one to three sentences" but that's instruction, not enforcement. max_output_tokens on the interruption API call is never explicitly set.
The Assessor's context is expensive — when the Assessor runs, it gets the Entity instruction string + full Grimoire + Chronicle retrieval + full Thread + task prompt. For a long session this could easily be 6,000-8,000 input tokens. Nobody costed this out.
No session cost tracking — the Wizard has no way to see how many tokens have been spent in a session, no cumulative cost display, and no warning when a session is approaching a budget threshold.
Entity sampling profiles set max_output_tokens but not max_input_tokens — there's no mechanism to prevent the context assembly from growing arbitrarily large before the distillation threshold fires.
The distillation threshold is fixed — 6,000 tokens, 6 message minimum. There's no adaptive behavior. A session asking rapid-fire long questions could accumulate 5,900 tokens and never trigger distillation, while still generating expensive API calls every turn.
No cost-per-model awareness — gpt-4o is roughly 15-20x more expensive per token than gpt-4o-mini. The router's smart_threshold (0.55) was set as a reasonable default but was never tuned against actual cost data.
What I'd recommend adding:

A Token Economy spec — a dedicated document covering: Chronicle injection budget (suggested: 1,200 token hard cap on retrieved entries), per-call input token estimation before the API call fires, session cost accumulator displayed in the status bar, a configurable session_budget_warning threshold, adaptive distillation (lower threshold when session cost is elevated), and interruption output caps hardcoded at 150 tokens maximum.

The good news: the infrastructure to implement all of this is already in place. The status layer can display cost. The router already estimates token counts. The distillation engine already has the threshold logic. It's mostly a matter of wiring existing pieces together and adding one honest accounting layer.

Two files. Here's where they go and what they do:

Konsole — Luminarious.colorscheme Drop into ~/.local/share/konsole/ and select it in Konsole → Settings → Edit Current Profile → Appearance. Void 
#0D0B0E as the terminal background, parchment as foreground. The 16 ANSI colours are mapped to the full Luminarious palette — crimson for red/errors, verdigris for green/success, aureate for yellow/warnings, steel blue for blue, violet for magenta, teal for cyan. Faint variants are darkened, intense variants are lifted.

Micro — luminarious.micro Drop into ~/.config/micro/colorschemes/ then activate with set colorscheme luminarious in the micro command bar (or add it to ~/.config/micro/settings.json).

The syntax mapping follows the lore logic:

Keywords — aureate gold. The signature voice of the machine.
Strings — verdigris. The colour of Chronicle retrieval — something being held, preserved.
Functions — amber glow. Active, doing work.
Types/classes — worn copper. Structure, architecture.
Numbers/constants — teal. Precise, fixed, exact.
Operators — violet. The Contrarian's colour. Signs that interrupt flow.
Imports/builtins — steel blue. The Archivist. Things retrieved from elsewhere.
Comments — mist. Inactive, secondary, background thought.
Errors — crimson. The Assessor's colour. Problems wear the Assessor's face.
Selection — black text on aureate gold. Unmistakable.
Line numbers — Umbra background, barely visible until the current line lights up in gold.
Markdown headings — full gold hierarchy, prose treated with the same reverence as code.
The whole environment — KDE, terminal, editor — now wears the same skin as the machine you're building.
