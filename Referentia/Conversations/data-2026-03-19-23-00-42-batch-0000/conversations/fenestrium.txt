**IdeaForge — Composition Model Design (pre-build)**

The core question is: *what data structure represents a nested layout, and how 
does the user build it?*

**The tree problem**

A Textual layout is a tree. `Vertical` contains `Label` + `Button`. 
`Horizontal` contains two `Vertical`s. The code output has to reflect that 
nesting — indented `yield` statements inside `compose()` methods. So the 
internal state needs to be a real tree, not a flat list.

**How the user builds it**

Three viable interaction models:

1. **Drag onto canvas** — visual, but complex to implement and easy to get 
wrong
2. **Click-to-add-child** — select a node in the tree, then pick a widget to 
insert as its child
3. **Outline/tree panel** — a dedicated hierarchy view where you click a node 
to select it, then add siblings or children from the widget browser

Option 3 is the cleanest fit for a code-output tool. It mirrors how you 
actually *think* about Textual layouts — as a tree — and the output maps 
directly to it. It also replaces Arbor cleanly: **the freed pane becomes the 
composition tree.**

**What the panes become:**

| Pane | Latin Name | New Role |
|---|---|---|
| Left | **Classis** | Widget browser + props (collapsed list when editing) |
| Centre-left | **Arbor** | Composition tree — the layout hierarchy 
(reclaimed name, new purpose) |
| Centre-right | **Specularium** | Live preview of selected node + full layout 
preview |
| Right | **Codex** | Generated Python for the full composed tree |

*Arbor* is actually the perfect name for the composition tree — it means 
tree. The file browser stole a name that was always meant for this.

**Code generation model**

Each node in the tree generates its own `yield` statement. Container widgets 
(`Horizontal`, `Vertical`, `Grid`, `ScrollableContainer`, `TabbedContent`) get 
a `with` block. Leaf widgets get a bare `yield`. The full output is one 
`compose()` method that reflects the entire tree.

**Constraints to hold:**
- Max nesting depth: 6 (beyond that, Textual layouts get unwieldy anyway)
- Root node must be a container widget
- Leaf widgets (Button, Label, Input etc.) cannot have children
- Selecting a node in Arbor focuses props in Classis and highlights that node's 
preview in Specularium

## Foundational Reconsiderations

**1. The uid counter is a module-level mutable variable that never resets.**

```js
let _uid = 1;
const mkNode = ...
```

`_uid` is declared at module scope and increments forever. In React's 
development mode, components remount and effects re-run. In any hot-reload 
scenario — which is exactly how this tool will be developed and extended — 
nodes created before a reload will have uid 1, 2, 3, and nodes created after 
will *also* start at 1, 2, 3. This produces silent uid collisions. `treeFind`, 
`treeAdd`, `treeDel`, `treePatch` all key on uid. A collision means the wrong 
node gets modified or deleted — silently, with no error, just incorrect 
behaviour.

**Fix:** Use `crypto.randomUUID()` or a timestamp-based id. One line change, 
eliminates the entire class of failure.

```js
const mkNode = (widgetId, overrides = {}) => ({
  uid: crypto.randomUUID(),
  ...
```

This is a Foundational Reconsideration because uid correctness underpins every 
tree operation in the application. Everything else is correct only if uids are 
unique.

---

**2. The widget registry is defined at module scope but `FLAT_WIDGETS` and 
`getWidgetDef` are computed once at load time from it. Adding a new widget at 
runtime is impossible — but more importantly, the registry has no 
validation.**

If a widget definition is malformed — missing `props`, missing `ascii`, a 
typo in `isContainer` — the failure mode is a silent crash somewhere in 
rendering or code generation, not a clear error at the definition site. There 
is no schema, no guard, no `console.warn` if a definition is incomplete.

This matters because you said you want to extend this. The first time you add a 
widget and something doesn't work, you will spend time debugging rendering 
before realising the definition was malformed.

**Fix:** A lightweight `validateWidget` call at load time that checks required 
fields and throws with the widget id if something is missing. Ten lines. Saves 
hours.

---

**3. `genCompose` calls itself recursively but `codeExtra` receives 
pre-rendered child strings, not nodes.**

```js
const genRichHelpers = root => {
  ...
  const node = findNodeById(root, "RichTable");
```

`findNodeById` finds the *first* `RichTable` in the tree. If you have two 
`RichTable` widgets, only one gets a helper. The second one generates 
`build_table()` call in its `yield` but there is only one `build_table()` 
definition in the output. The generated code will run and call `build_table()` 
twice, returning the same table both times — which may or may not be what the 
user wanted, with no indication either way.

**Fix:** Name helpers by node uid or id prop — `build_table_my_rtable()`. 
Make `genRichHelpers` walk the full tree and emit one named helper per rich 
widget that needs it.

## Tactical Revisions

**4. The `Select` widget generates no working code for its `options` prop.**

Look at `genCompose` for `Select`. The `options` prop is a comma-separated 
string like `"Alpha,Beta,Gamma"`. The generated output emits 
`options="Alpha,Beta,Gamma"` as a kwarg — but `Select` in Textual does not 
take a string. It takes a list of `(label, value)` tuples, or a `SelectType`. 
The generated code for `Select` will crash on import with a `TypeError`. This 
is the same class of problem as the old `ComposeResult` bug — silent 
generation of invalid code.

**Fix:** `Select` needs a `codeExtra` or its options need to be pre-processed 
into a `OPTIONS = [...]` list above the class, similar to how `RichTable` gets 
`build_table()`.

**5. `RadioSet` has the same problem.** It generates `options="Option A,Option 
B,Option C"` but `RadioSet` takes `*buttons` positional args, not a string. 
Generated code crashes.

**6. The `classes` prop on `Vertical` and `Horizontal` emits 
`classes="my-class"` as a kwarg.** Textual's `Widget.__init__` takes `*classes` 
as positional strings, not a `classes=` keyword argument. 
`Widget(classes="foo")` does not work — it should be `Widget("foo")` or the 
CSS class string needs different handling. This is a silent failure that 
produces a widget with no class applied and no error message in many Textual 
versions.

**7. `handleCopy` has a stale closure over `codeText`.**

```js
const handleCopy = useCallback(() => {
  navigator.clipboard.writeText(codeText).catch(()=>{});
  ...
}, []);  // ← empty dependency array
```

`codeText` is computed from `tree` and `exportMode` but `handleCopy` closes 
over it with an empty `[]` dependency array. The `useCallback` will never 
update its closure. The copy button will always copy the code from the *first 
render*, which is the empty state placeholder. This is a classic React stale 
closure bug.

**Fix:** Add `codeText` to the `useCallback` dependency array, or remove 
`useCallback` entirely since `handleCopy` is not a performance-critical 
function.

**8. The `Columns` Rich widget generates `Columns([…])` — a literal 
ellipsis.** There is no guidance in the output about what to put there. Unlike 
`RichTable` which gets a `build_table()` helper, `Columns` just emits an 
unfillable placeholder. The user will copy this code, run it, and get a 
`TypeError` on the `[…]` which is not valid Python.

**Fix:** Generate a `COLUMNS_ITEMS = []` placeholder list with a comment, and 
reference it in the constructor call.

Now the architecture. This needs to be thought through properly because the 
three preview modes are the crux of everything.

**Preview Mode 1 — Subprocess (ANSI capture)**

Fenestrium generates the current widget code dynamically, writes it to a temp 
file, spawns a subprocess running a minimal headless Textual app, captures the 
ANSI output using `textual run --screenshot` or by capturing stdout with a 
custom `App.export_screenshot()` call, then displays it in a `Static` pane. 
This gives true isolation — the previewed widget cannot crash Fenestrium. The 
cost is latency: ~300–800ms per render. Triggered on demand, not on every 
keystroke.

**Preview Mode 2 — Inline mounting**

Fenestrium dynamically constructs the widget tree using `importlib` / `exec` in 
a sandboxed namespace, then mounts the result into a dedicated 
`ContentSwitcher` or `ScrollableContainer` pane inside its own layout. Instant 
updates. Risk: a misbehaving widget could affect Fenestrium's own layout or 
event loop. Mitigated by catching exceptions at mount time and falling back 
gracefully.

**Preview Mode 3 — SVG export**

Uses Textual's built-in `export_screenshot(path)` on the subprocess app, which 
outputs a proper SVG. Displayed via a `Static` with the SVG content or opened 
externally. Slowest but most faithful — pixel-perfect, exportable, shareable.

**Autosave architecture**

On `App.on_exit`, serialize the current tree to 
`~/.config/fenestrium/session.json` as a simple recursive dict. On 
`App.on_mount`, check for that file and restore if present. A 
`~/.config/fenestrium/` directory gets created on first run. Crash safety: 
write to a `.tmp` file first, then `os.replace()` atomically.

**Fenestrium — Python. The real one.**

2,647 lines across 14 files. Install and run on CastrumDigitos:

```bash
pip install textual rich pyperclip
cd wherever-you-put-it
python -m fenestrium
```

**What's in each module:**

`core/registry.py` — 29 widget definitions across Layout, Input, Display, 
Navigation, and Rich. Self-validating at import. Every widget is data, not 
scattered code.

`core/tree.py` — pure immutable tree operations. `make_node` uses `uuid4` — 
no uid collision possible. `tree_map`, `tree_add`, `tree_delete`, `tree_patch`, 
`tree_find`, `tree_walk`.

`core/codegen.py` — the engine. Preamble/body split architecture means 
module-level constants (Select OPTIONS, Sparkline DATA) are always above the 
class, never inside `compose()`. TabbedContent generates proper `TabPane` 
wrappers. All positional args correct. All tested.

`core/session.py` — atomic autosave via `.tmp` + `os.replace()`. Loads on 
mount, saves on exit. Corrupt sessions silently reset.

`preview/` — three modes. Subprocess spawns an isolated headless app and 
captures SVG. Inline mounts the widget directly in-process. SVG exports to 
`~/.config/fenestrium/exports/` and opens with `xdg-open`.

`widgets/` — four Textual panes wired together through messages. All 
keybindings in `BINDINGS`. Fully keyboard-driven.

**Honest caveat:** the pane widgets are complete and architecturally correct, 
but the TCSS will need tuning once you run it — widths, colours, and 
Textual-specific layout details always need adjustment against a real terminal. 
The core and codegen are solid and tested. The UI is the starting point, not 
the finished product.
