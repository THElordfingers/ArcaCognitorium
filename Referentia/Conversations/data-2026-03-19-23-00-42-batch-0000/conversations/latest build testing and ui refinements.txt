Good. Here's the full picture from the actual code:

---

**GRIMOIRE** — permanent identity layer, lives in 
`storage/grimoire/grimoire.json`

Never compressed, never auto-modified, injected into every conversation context 
within an 800 token budget. Three sources: `manual` (Wizard-written, fully 
editable), `assessor` (written by the Background Assessor, read-only for the 
Wizard), `archivist` (same protection). The Assessor fires every 5 turns, 
analyses the recent thread + existing Grimoire entries, produces JSON 
observations, deduplicates against existing content using a token overlap 
similarity check, and writes new ones. It's building a portrait of *who the 
Wizard is* — stable traits, preferences, patterns.

---

**CHRONICLE** — long-term retrievable memory, lives in 
`storage/vectors/vectors.pkl`

A vector store using `all-MiniLM-L6-v2` embeddings and cosine similarity 
search. Three things write to it: every completed turn (raw `USER/ASSISTANT` 
text, written automatically in `_assistant_task`), the Archivist (synthesised 
observations at turn 8, looking for meaningful moments and patterns rather than 
raw exchanges), and Distillation (muscle sentences extracted when context 
compression fires). At query time it filters by conversation ID and thread ID, 
scores by cosine similarity, and returns the top-k above a minimum relevance 
score (currently 0.20). The Assessor also reads from it for cross-session 
context before writing to the Grimoire.

---

**DISTILLATION** — context compression engine, `memory/distillation.py`

Two modes. `rollup()` runs continuously via 
`ConversationStore._maybe_summarize()` — triggered after 18 messages, keeps 
the last 10, compresses the rest into a rolling thread summary using Haiku. 
This summary lives on the thread object and gets prepended to context. 
`distill()` is the full pipeline — classifies messages as fat (filler, 
acknowledgements) or muscle (decisions, conclusions, constraints), extracts 
muscle sentences to the Chronicle, then compresses everything to a summary. 
Fat/muscle classification uses regex patterns. The muscle patterns specifically 
look for decision language, constraint language, named vocabulary, and 
project-specific terms.

---

**How they connect at runtime:**

Every turn: raw exchange → Chronicle. Every 5 turns: Assessor reads Chronicle 
+ Grimoire → writes new observations to Grimoire. Every 8 turns: Archivist 
reads thread → writes synthesised entries to Chronicle. When context grows 
past ~18 messages: rollup fires, compresses oldest messages to thread summary. 
When context approaches token limit: full distillation fires, muscle goes to 
Chronicle. At context build time: Grimoire injection prepended, Chronicle 
queried for relevant past fragments, both fed into the model's context window.

LordFingers: yeah lets start with the first step, accumulation. we can expand after. what

Claude:  The trigger keeps each entity's memory **semantically coherent** — they only 
accumulate observations that are actually relevant to their domain. Without 
triggers, every entity writes on every turn and you end up with noise. A few 
examples of why it matters:

The **Pessimist** storing "Wizard accepted a risk flag" is meaningful. The 
Pessimist storing "Wizard asked about French cooking" is garbage. The trigger 
ensures the store stays signal-dense within the token budget.

The **Contrarian** remembering "Wizard defended this premise three times" tells 
you something about conviction. The Contrarian remembering every turn it 
happened to be active tells you nothing.

The **Archivist** tracking what topics the Wizard has retrieved from the 
Chronicle means it can notice patterns — "Wizard returns to this subject 
repeatedly." Without a trigger it's just a log.

The practical benefit: with 150–300 tokens per entity, you can't afford 
noise. Triggered writes mean when an entity reads its own memory, every entry 
is actually relevant to how it should behave.

The tradeoff: triggers add complexity — you have to define and implement the 
condition for each entity. For a first pass, a simpler middle ground works well 
— **entity writes only when it speaks or interrupts**, not on every turn. 
That's one condition instead of eight, still keeps memory entity-specific, and 
still produces coherent stores because an entity's memory of its own 
interactions is inherently relevant to its domain.

That's probably the right starting point — write on speak/interrupt, read on 
speak/interrupt. Then layer in domain-specific triggers for individual entities 
once you've seen how the basic accumulation behaves in practice.
