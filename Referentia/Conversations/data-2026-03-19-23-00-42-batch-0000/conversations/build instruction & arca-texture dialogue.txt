---

**What a "session" is in ClaudeBox terms:**

Claude has no persistent memory between API calls. Each call is stateless. A 
"session" in ClaudeBox is essentially a managed conversation history — a list 
of messages (user/assistant turns) that gets sent with every API call to 
simulate continuity. ClaudeBox holds that list in memory for the duration of 
the application's runtime.

So when you talk to Luminarious, ClaudeBox is sending:
- Luminarious's compiled system prompt
- Every prior turn of that conversation
- Your new message

That's the "session." It's not a Claude-side concept — it's entirely 
client-side state management.

---

**The implication for entity memory:**

This means entity "memory" right now is **ephemeral** — it lives only as long 
as the app is running. When you restart, it's gone unless it's been written to 
disk somewhere (Chronicle, EntityMemory JSON, Grimoire etc.).

What you're describing — entities maintaining a working individual memory of 
the ongoing plot and relationships — requires **reconstructing context on 
session start** from those persistent stores. The session gets seeded with 
distilled history, not the raw full conversation.

The balance you're intuiting:
- Too much history in the session = token bloat, cost, slower responses
- Too little = entity loses the thread, feels amnesiac
- The Distillation layer exists precisely to solve this — compress the 
Chronicle into a dense context seed
