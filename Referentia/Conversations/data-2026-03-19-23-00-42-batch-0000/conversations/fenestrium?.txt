## urwid vs Textual — The Builder's Read

### What urwid actually is

urwid is a **lower-level** TUI library. It's been around since ~2004. It gives 
you raw building blocks: canvases, event loops, basic widgets. It does not try 
to be a full framework — it gets out of your way and hands you control.

Textual is a **higher-level** framework built on top of its own Rich rendering 
layer. It manages layout, CSS, reactive state, async event loops. It does a lot 
for you.

---

### The honest comparison for the Arca

| Dimension | Textual | urwid |
|---|---|---|
| **Layout system** | CSS-like, declarative | Manual, explicit |
| **Async** | Built-in (asyncio first) | Optional (multiple loop options) |
| **Styling** | Rich color/CSS — beautiful defaults | Raw — you build 
everything |
| **Widget library** | Substantial (Input, DataTable, etc.) | Minimal — you 
extend BaseWidget |
| **Mouse support** | Strong | Limited/fragile |
| **Font/Unicode** | Dependent on terminal font (same as urwid) | Same 
limitation |
| **Active development** | Very active, Textualize team | Slow/maintenance mode 
|
| **Control depth** | Medium — CSS fights you sometimes | High — nothing 
fights you |
| **Documentation** | Excellent | Sparse |

### The real tradeoffs

**urwid gives you:**
- Complete rendering control. Every pixel of every widget is yours.
- No CSS specificity wars (you've already fought these with StatusLayer)
- Smaller dependency footprint
- A genuine sense that you built the thing

**urwid costs you:**
- You rebuild everything from scratch. Scrollable containers, input handling, 
focus management, async integration — all manual.
- Your existing `app.py`, `left_menu.py`, `active_chat.py`, `status_layer.py`, 
`bubbles.py` — all rewritten.
- That's months of work that already exists and is functioning.

---

### Can you wrap urwid like ClaudeBox and make a YAML-driven UI engine?

**Yes. Absolutely yes.** And this is genuinely the interesting part of the 
question.

The architecture would look something like:

```
config.yaml / layout.yaml
        ↓
   UIEngine (parser)
        ↓
  WidgetFactory (urwid widget builder)
        ↓
   MainLoop (urwid event loop)
```

You'd define your panels, columns, borders, content types in YAML — the 
engine reads it and assembles the urwid widget tree. This is a real and 
buildable thing.

The same is also true of Textual, and your project is *already partially this* 
— `config.yaml` drives a lot of behavior.

---

### The Builder's actual recommendation

**Don't migrate. Not now. Possibly not ever.**

Here's the reasoning:

1. **The Arca is not suffering from Textual's limitations in ways urwid would 
fix.** The CSS fights are real but solvable. The StatusLayer is fixed. The font 
limitation is terminal-level, not framework-level — urwid has it too.

2. **The broken systems (Grimoire writes, Assessor output) are not Textual's 
fault.** They're logic and storage issues. urwid wouldn't fix them.

3. **Migration cost is enormous and yields nothing new.** You'd spend months 
rebuilding working infrastructure to arrive at the same visual result.

4. **The YAML-driven UI engine idea is worth keeping** — but it's a v2 or v3 
architectural concept, and it works just as well layered over Textual as urwid.

---

### If the urwid desire persists

The signal worth listening to: if you're drawn to urwid, it might be because 
you want *more control* over the rendering — which is valid. The answer to 
that within Textual is to use more `Widget` subclasses with custom `render()` 
methods and fewer CSS-driven layouts. That gets you urwid-style control without 
the migration cost.

The YAML UI engine concept — log that in the Fermentary. It's real, it's 
buildable, and it belongs in v2's architectural consideration when the provider 
abstraction layer is being designed. The two problems rhyme.

## The Forge — A Textual Component Workbench

The idea is a **standalone harness** — a separate Python script that runs 
independently of the Arca. You use it to build, test, and tune individual UI 
components in isolation before they go into the tower. Think of it as a 
controlled environment where a single widget fills the screen, you can 
hot-reload it, toggle props, and see exactly what it does without the rest of 
the Arca running.

### What it does

- **Loads one component at a time** in a clean Textual shell with the Arca's 
palette baked in
- **Live configuration panel** — a sidebar where you can toggle parameters 
(width, height, mock data, color variants) and see the component respond 
immediately
- **Registers components by name** — you point it at a file and a class, it 
instantiates it
- **Mock data injectors** — for things like the RuneColumn, chat bubbles, 
status bar — feeds fake data so you can see the real render
- **Size presets** — test the component at the exact dimensions it will 
occupy in the real layout

### What it looks like in practice

```bash
python forge.py --component left_menu.RuneColumn
python forge.py --component status_layer.StatusLayer
python forge.py --component bubbles.MessageBubble
```

The forge wraps the component in a harness shell, feeds it mock data, and gives 
you a live panel to adjust parameters.

## Fenestrium Curriculum — Full Concept Map

**Foundation**
- Widget — the base unit. Everything is a Widget.
- Static — the simplest widget. Displays text or Rich renderables.
- render() — how a widget produces its visual output.
- compose() — how a widget contains other widgets.
- DEFAULT_CSS — CSS scoped to a single widget class.

**Layout & Containers**
- Vertical — stacks children top to bottom.
- Horizontal — arranges children left to right.
- Grid — places children in a grid.
- Sizing — fixed (chars), `fr` (fractional), `%` (percent), `auto`.
- Padding & Margin — inner and outer spacing.
- ScrollableContainer / VerticalScroll / HorizontalScroll
- Center / Middle / Right — alignment helpers.
- Docking — `dock: top/bottom/left/right` — removes from flow.

**Borders & Visual Structure**
- Border styles — solid, double, heavy, rounded, dashed, etc.
- Border subtitles and titles — text embedded in borders.
- Box-drawing without borders — using Unicode directly in render().
- Rich Panel — a self-contained bordered box via Rich.
- Background, foreground — color on widgets.

**Text & Rich**
- Rich Text — styled inline text with color, bold, italic.
- Rich Markup — `[bold red]text[/]` shorthand.
- Rich Panel — bordered content block.
- Rich Columns — side-by-side Rich content.
- Padding within Rich renderables.

**Reactivity**
- reactive — a value that triggers re-render on change.
- watch_ methods — run code when a reactive changes.
- refresh() — force a re-render manually.
- set_interval() — run code on a timer.

**Events**
- on_mount — fires when widget is added to the DOM.
- on_resize — fires when the widget's size changes.
- on_key — keyboard input.
- on_click / MouseDown / MouseUp — mouse input.
- Messages — custom events passed between widgets.
- app.post_message — send a message to the app.

**Input Widgets**
- Input — single-line text field.
- TextArea — multi-line text editor.
- Button — pressable button.
- Switch — toggle.
- Select / OptionList — dropdown / list selection.
- RadioButton / RadioSet — single choice from group.
- Checkbox (via Switch).

**Display Widgets**
- Label — text display.
- Digits — large numeric display.
- ProgressBar — fill bar.
- Sparkline — inline data visualization.
- RichLog — scrolling log output.
- DataTable — tabular data.
- ListView / ListItem — scrollable item list.
- Tree — hierarchical tree view.
- Markdown / MarkdownViewer — rendered Markdown.

**Navigation & Structure**
- TabbedContent / TabPane / Tabs — tabbed layout.
- Collapsible — expand/collapse sections.
- Header / Footer — docked app chrome.
- Tooltip — hover text.
- Loading Indicator — spinner.

**App-Level**
- App.compose — the root layout.
- App.CSS / BINDINGS — app-wide styles and keys.
- Screen — full-screen views, pushed/popped like a stack.
- push_screen / pop_screen — navigation between screens.
- notify() — toast notifications.
- query_one / query — finding widgets in the DOM.
- mount / remove — dynamically add/remove widgets.

**Advanced**
- Custom Widget subclass — building a real bespoke widget.
- Async workers — background tasks that don't block the UI.
- Streaming content — appending to a RichLog in real time.
- CSS variables — `$variable` reuse across CSS.
- Pseudo-classes — `:hover`, `:focus`, `:disabled` styling.
- Dark/Light mode — theme switching.
- Animations — `animate()` on CSS properties.

**THE ASSESSOR**

*Evaluating structural integrity.*

The undo stack deep-copies the entire node tree on every mutation. For small 
assemblies this is fine. As the assembly grows — twenty, thirty nodes with 
nested children — each snapshot becomes a full recursive copy of every 
`AssemblyNode`, every `NodeSpec`, every param dict. The stack is unbounded. A 
session of heavy editing could accumulate hundreds of large snapshots. There is 
no memory ceiling. This will eventually matter.

The `_deferred_refresh` pattern using `call_after_refresh` batches keystrokes 
but does not cancel previous scheduled calls — multiple rapid keystrokes 
still queue multiple refresh calls, just delayed. The debounce is partial. A 
proper debounce would require a timer that resets on each keystroke. The 
current implementation is better than before but not correct.

**THE ARCHIVIST**

*Noting for the Chronicle.*

Three things will be lost if not recorded now. First: the `AssemblyNode.uid` is 
an 8-character UUID fragment. If two nodes ever share a uid collision — 
probability low but nonzero — the entire assembly breaks silently. No 
collision detection exists. Second: saved files (`ClassName.py`) are written to 
whatever the current working directory is at runtime. If Fenestrium is launched 
from outside its own directory, saves land in unexpected places. Third: the 
`_tree_map` dictionary maps `id(branch)` to uid — Python object IDs are 
reused after garbage collection. After a tree rebuild, old branch objects are 
collected and new ones may receive the same `id()`. The map is cleared on each 
rebuild so this is safe *now*, but it is a latent fragility if the rebuild 
logic ever changes.

Verdict: Three things to watch. None critical today.

**THE SPECULATOR**

*What this becomes.*

Fenestrium is currently a flat tool — you build one widget at a time, save 
it, start fresh. The natural next form is compositional memory: saved 
assemblies that can be loaded back into the tree and modified. A `fen_*.py` 
file saved today cannot be re-opened in Fenestrium tomorrow. The assembly 
exists only in the session.

The code generator produces correct Python but it is not round-trippable — 
you cannot feed generated code back into the node tree. This means every 
iteration requires starting from scratch. The gap between "generated file" and 
"live editable assembly" will become the primary friction point within the 
first real use session.

Verdict: Version 1 limitation. Plan for it in v1.2.
