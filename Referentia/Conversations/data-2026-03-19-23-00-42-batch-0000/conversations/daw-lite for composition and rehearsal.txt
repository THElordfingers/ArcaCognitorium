Plain JS + CSS is fine for a proof of concept but will become painful as the

Claude:  That balance you're describing — zero-friction default flow with deep 
configurability underneath — is actually the hardest design problem in tools 
like this. Most software picks one or the other. Getting both right is what 
separates tools people actually use from tools people admire and abandon. So 
it's worth thinking carefully about how that tension shows up at every layer.

**The "just sit down and write" path**

The ideal new session flow is something like: open the app, name your song, 
pick a key and a vibe, and immediately have something useful in front of you. 
That means smart defaults everywhere. A new session could auto-populate a 
standard rock band lineup, a 4/4 time signature, a common tempo range, and 
maybe even suggest a chord progression based on the key and mood. The user 
shouldn't have to configure instruments they probably already want. They should 
be able to override everything, but touch nothing if they don't want to.

A "quick start" mode versus "advanced setup" toggle at the session creation 
screen could handle this gracefully — one path for people who want to dive 
in, one for people who want to configure from scratch.

**The section/arrangement layer deserves more thought**

The block-based song structure you described is good, but there's a lot of 
useful functionality hiding in there. Sections could have color coding for 
visual scanning at a glance. You could support section linking — where a 
verse block in slot 2 and verse block in slot 5 are instances of the same 
section, so edits propagate. Or you can deliberately break that link and let 
them diverge. This is how arrangement in real songwriting works: "the second 
verse is the same as the first, except the last bar." You'd also want a song 
map view — a horizontal timeline showing the full arrangement at a glance — 
which doubles as a navigation tool for jumping to a section's notation.

**Chord progression flow is underspecified**

You mentioned a global chord progression but this is a meaty feature. The most 
useful implementation would be a progression builder per section — you drag 
or click chords from the theory-informed palette into a bar-by-bar grid, assign 
durations, and that progression then becomes the backbone the vocal and guitar 
notation layers reference. It would show up as a chord chart above the vocal 
line, and optionally as slash notation or guides above the guitar tab. 
Progressions could be saved and loaded as presets. Common progressions (I-IV-V, 
I-V-vi-IV, etc.) could be offered as starting points with the actual chords 
transposed to the current key automatically.

**The fretboard needs a few modes people won't think to ask for**

Beyond scale display and root notes, some genuinely useful display modes: 
highlighted chord tones for the current progression chord (so as the user is 
writing a lead, the fretboard shows what notes are "inside" at that moment), a 
comparison mode showing two scales or modes simultaneously, a capo mode that 
shifts the visual display, and a "reachable from this position" highlight that 
shows what notes are accessible without a position shift — useful when you're 
writing and want to stay in a box.

**Techniques and articulation are deeper than they appear**

For guitar tab specifically, the set of notation symbols is large: hammer-ons, 
pull-offs, slides (up and down, with arrival note or open-ended), bends (full, 
half, quarter, bend-and-release, pre-bend), vibrato, tapping, harmonics 
(natural and pinch), palm muting, string skipping, whammy notation, and rake. 
Each has a visual representation in tab and some affect note duration and pitch 
in ways that need to be encoded. You don't need to support all of these on day 
one, but your data model for a note event needs to be able to accommodate them 
without a redesign. A technique field that accepts a structured set of flags 
and parameters is the right call.

**Drums need their own thinking**

You mentioned a grid format, which is right. The standard grid maps rows to 
drum/cymbal voices and columns to rhythmic subdivisions. But a few things are 
worth adding: velocity indication (ghost notes versus accents — this is core 
to how drummers read parts), rudiment suggestions or a rudiment library, the 
ability to define custom voices for non-standard kits, and polyrhythm support 
if bars have different time signatures. Drum fills should be notatable as 
distinct from groove patterns, and the section system should be able to flag 
"fill here" as a cue even when the exact fill is left to the player.

**Vocals are the most neglected instrument in software like this**

A vocal interface should show lyrics aligned to a chord chart, with the ability 
to place syllables against the bar grid so timing is clear. Melody can 
optionally be notated — either in a simplified pitch grid (not full standard 
notation) or just as a contour suggestion. Vocal harmonies are worth supporting 
— a second or third voice track that shows the interval relationship to the 
lead. Range indicators based on a singer profile would be a nice touch — the 
system could flag if a melody goes above or below the vocalist's defined range.

**Missing features worth considering**

A reference audio link per section — just a URL to a YouTube clip or a file 
— so you can say "the feel of this bridge is like this." No playback in the 
app, just a pointer. Incredibly useful in a rehearsal context.

A notes and annotations layer — freeform text attached to any section or bar. 
"Play this loose," "drummer comes in here," "key change discussion." This is 
how real musicians communicate and it's almost never in notation software.

A version history or snapshot system. Not full undo-redo (though you want that 
too), but the ability to name and save a state of the whole document — 
"version before we tried drop D," "arrangement attempt 2" — and flip between 
them.

A setlist view that sits above the song level — where you can group songs, 
see all the keys and tempos at a glance, and note transitions between songs. 
Slightly outside the core scope but a natural extension for a band context.

Transposition tools at every level. If someone decides to change the global 
key, the system should offer to transpose all the written notation 
automatically, with a preview of what changes and the option to exclude certain 
instruments.

Print templates — different layouts for different use cases. A guitarist 
wants their tab with chord names above it. A vocalist wants lyrics with chord 
symbols, big and readable. A drummer wants just the groove grid. These should 
be definable and savable.

**The feel of the app**

Given you want it to feel friendly and frictionless, a few UX principles worth 
baking in early: nothing should be more than two clicks from the main flow. 
Every destructive action should be undoable. The app should never lose work — 
autosave to a local draft constantly. Tooltips and contextual help should be 
present but not intrusive — the kind of thing you hover over when confused, 
not the kind of thing that pops up uninvited. Keyboard shortcuts for everything 
in the notation layer, because anyone who uses it heavily will want to keep 
their hands off the mouse.
