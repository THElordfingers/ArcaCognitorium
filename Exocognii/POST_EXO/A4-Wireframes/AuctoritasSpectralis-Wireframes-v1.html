# AUCTORITAS SPECTRALIS ### Codexium Chromaticus — Redesign & Revision Plan ### Bureau of Spectral Compliance · Triumviratus Aestheticus Imperialis --- > *The apparatus does not merely select colours. It governs them.* > *It arbitrates. It ratifies. It remembers. It does not explain itself.* > *It is felt.* --- ## I. PREAMBLE This document is the complete design plan for the revision of Auctoritas Spectralis — Bureau I of the Triumviratus Aestheticus Imperialis. It is prepared for Council Review and submitted to the ratification process intact. The document addresses four mandates simultaneously: - What Auctoritas Spectralis must become as the Central Colour Authority of the Cogniverse - How the A4 Common Shell design applies to Bureau I specifically - How the Codexium Chromaticus feature set must be revised to honour that vision - What the complete workflow looks like, from first launch to sealed ratification Luminarious is watching. This document does not waste his time. --- ## II. THE CENTRAL COLOUR AUTHORITY — VISION STATEMENT A central colour authority is not a palette picker. It is an instrument of governance. Its role in the Cogniverse is to: **Own** the canonical colour contract — `theme.json` — and be the sole writer of it across the entire Exocognii Suite. Every other application reads. Only Bureau I writes. **Generate** colour palettes with perceptual rigour — in OKLAB space, not HSL, not RGB. The human eye is the final arbiter and OKLAB honours it. Harmony algorithms govern the relationships between tokens. Contrast algorithms enforce legibility. **Evaluate** every meaningful foreground/background pairing against six contrast metrics simultaneously. Not one. Six. Failures surface immediately and are impossible to miss. **Ratify** palettes with cryptographic identity — SHA-256 seal, Latin designator, full registry entry. A sealed palette is a permanent record. **Distribute** the sealed palette to every format the Cogniverse requires: `theme.json`, `theme.qss`, `theme.md`, `theme.css`. **Remember** everything. The Chromatic Registry is not a cache. It is an archive. Every palette ever ratified lives there, queryable, loadable, forkable. This is what Bureau I must be. The current implementation has the correct bones. The revision builds the right body around them. --- ## III. ALIGNMENT WITH COGNIVERSE PHILOSOPHY The Tower's operating principles apply directly to Bureau I: **Emergence over instruction.** The Specularium Vivum does not explain what the palette looks like. It shows it. The Wizard discovers the palette's character by seeing it rendered in real UI surfaces — not by reading hex values. **Information is discoverable, not explained.** Contrast scores appear in context. Failures are visible in the matrix without being narrated. The apparatus does not announce itself. **Nothing is truly lost.** The Detritus principle applies: no palette is ever deleted. Rejected palettes enter the registry with status REJECTED. The Chromatic Registry is a sediment layer, not a bin. **The apparatus is an organism, not a sculpture.** Bureau I responds to what the Wizard feeds it. It derives, evaluates, and offers — but the Wizard ratifies. The machine proposes. The sovereign disposes. **Ordo Discordia, Cosmos Inania.** The colour generation system is deliberately probabilistic within mathematical constraints. The harmony algorithms introduce structured randomness. Running Complementary twice produces two different palettes. Both are valid. Neither is random. --- ## IV. PALETTE MODEL — THE REVISED ARCHITECTURE The current implementation derives all tokens mathematically from a single BG/FG pair using fixed ratios. This is the correct foundation. The revision extends it in two directions. ### VI.I Token Roles (unchanged) The 10-token hierarchy is maintained: ╭──────────────────┬──────────────────────────────────────────────────────╮ │ Token │ Role │ ├┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┼┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┤ │ c_bg / Void │ Primary background. This means a violet palette still produces a red Sanguis and a blue-green Viridis — colours that may be harmonically unrelated to the rest of the palette. In the revised model, the harmony algorithm governs all derived tokens, including Sanguis and Viridis. Their hue relationships derive from the base pair's hue angle, offset according to the selected harmony model. The Wizard can lock any token to override this behaviour. Example: a Complementary palette with a gold base pair (hue ~91°) will produce a Viridis at ~271° (blue-purple) rather than the fixed 195° teal. The result is harmonically coherent even in the accent tokens. ### VI.III Token Lock Each derived token in the palette list has a lock toggle. A locked token is: - Excluded from re-derivation when GENERATE fires - Highlighted with a gold lock indicator in the palette list - Carried forward when switching harmony algorithms ### VI.IV Generated Nomen Each token receives a generated two-word Latin name reflecting its actual perceptual character (hue family + lightness stratum). The Nomen updates on every derivation. It is distinct from the token role label. Example: the Aurum slot in a given palette might receive the Nomen "Chryseus Lucidus." The same token role in a different palette might receive "Solaris Candidus." The Nomen is stored in the registry alongside the token hex on ratification. --- ## VII. INTERACTION WITH THE EXOCOGNII SUITE Bureau I sits at the base of the Triumviratus. Its outputs are consumed by Bureau II (Agentia Architecturalis) and Bureau III (Departamentum Documentalis). Both read `theme.json` but do not write it. Beyond the Triumviratus: **PRAESIDIUM** reads `theme.json` to skin its widget canvas. When Bureau I seals a new palette, PRAESIDIUM receives the Mundana State Bus notification and reloads its QSS without requiring a restart. **GNOSIUM EXANIMA** (when built) will display entity portraits and UI chrome skinned to the current theme. It reads `theme.json` on launch and on change events. **The Tower** itself does not skin to `theme.json` at present. The Tower's Textual TUI uses its own CSS. This is noted as a future alignment task — the Chromata Terminalis palette in the TUI already maps to the same token values as the desktop system. **Exvacua Loricum** (when built) will store palette designators and Nomen as lore canon entries. The naming layer of Bureau I feeds the lore layer of the Tower. --- ## X. WHAT THE CURRENT IMPLEMENTATION GETS RIGHT These are the decisions that must be preserved in the rebuild: - OKLAB as the colour space. This is rare and correct. - The 10-token hierarchy. The roles are well-defined. - SHA-256 seal + Latin designator. Palette identity is properly handled. - Multi-format export (json, qss, md). The contract is properly distributed. - Six-metric contrast scoring. No other tool in the Cogniverse does this. - The generated Nomen system. Naming derived from perceptual character. - The Chromatic Registry as SQLite. Persistent, queryable, auditable. --- ## XI. WHAT THE REBUILD ADDRESSES - Shell: The Common A4 Shell — Title Legend, Feature Menu, context toolbar. Single Feature Presence. No everything-on-one-screen. - Harmony engine: Harmony algorithms govern *all* derived tokens, not just the base pair. Crimson and Viridis derive from the base pair's hue. - Token lock: Per-token lock in the derived palette list. - Specularium: Multiple display contexts. More real estate. All 10 tokens explicitly exercised. - Bibliotheca: Library as a first-class feature, not a collapsible drawer. - Help: Each feature has a dedicated, navigable help section accessible from its toolbar. --- ## XII. FEATURES NOT INCLUDED The following are explicitly out of scope for this revision: - Vision simulation (deuteranopia, protanopia, achromatopsia) — removed per Wizard directive. Was present in v1.0, will not return. - Multiple palettes in a single session — the session model is one working palette at a time. The Bibliotheca handles historical access. - Colour blindness accessibility reporting — not a stated requirement of the Cogniverse. Contrast metrics serve the legibility mandate. --- ## XIII.
